## AWS Security Hub Terraform Module

This module enables AWS Security Hub with comprehensive security monitoring and alerting capabilities.

### ⚠️ Important Dependencies

**AWS Config is REQUIRED** for Security Hub standards to work properly. Without AWS Config:
- Security Hub standards cannot evaluate resource configurations
- You won't get accurate findings for networking, IAM, and EC2/EKS misconfigurations
- Security scores won't appear in Security Hub

**AWS Inspector v2 is RECOMMENDED** for EC2/EKS/Lambda vulnerability scanning:
- Scans EC2 instances and container images for vulnerabilities
- Findings are automatically sent to Security Hub
- Essential for comprehensive EC2/EKS/Lambda security coverage

**AWS GuardDuty is OPTIONAL** for threat detection:
- Monitors for malicious activity and unauthorized behavior
- Provides intelligent threat detection for your AWS infrastructure
- Findings are automatically sent to Security Hub
- Disabled by default (`guardduty.enabled = false`)

**Amazon Macie v2 is OPTIONAL** for data security and privacy:
- Discovers, classifies, and protects sensitive data in S3 buckets
- Uses machine learning to identify sensitive data
- Findings are automatically sent to Security Hub
- Disabled by default (`macie.enabled = false`)

By default, Config and Inspector are enabled (`config.enabled = true`, `inspector.enabled = true`), while GuardDuty and Macie are disabled (`guardduty.enabled = false`, `macie.enabled = false`).

### Grouped security alerts and daily digest

`finding_delivery.notification_mode = "grouped"` reuses the existing EventBridge router, DynamoDB ledger, two SNS topics, Slack subscription, Opsgenie API notifier, and 15-minute Security Hub reconciliation worker. It does not create a second alerting pipeline. Inspector container findings group by account, Region, project, environment, repository, vulnerability ID, and package; image digests and finding IDs remain in the ledger. Other Inspector findings group by stable workload target, GuardDuty by stable finding ID with threat type and resource in the alert details, and compliance findings by control and resource group. A finding with multiple resources contributes all resource IDs to the digest count. Unknown vulnerability IDs remain finding-specific.

For shared ECR repositories, `finding_delivery.deployment_inventory` can supply the **displayed** environment from a short-lived S3 snapshot of running Kubernetes pod image IDs, including init containers. The snapshot must cover every configured cluster and match the exact ECR account, Region, repository, and digest. A complete fresh snapshot with no match displays `No running workload found`; an unavailable, stale, or incomplete snapshot displays `Unverified`. This display value never changes the incident alias or paging policy. The inventory publisher must refresh the object more often than `max_age_seconds` and upload it only after all configured clusters were scanned successfully.

Grouped mode uses separate identities: the remediation key retains repository, CVE/GHSA, and package, while the Opsgenie incident key uses account, Region, project, environment, repository, and incident category. CRITICAL Inspector container findings with unverified deployment or exposure create one P2 investigation per application by default, with one immediate Slack message per priority tier. Additional CVEs update that incident without a new alert or repeated note. A security-owner emergency vulnerability override can promote the same incident to P1. `paging.ecr_deployment_lookup_enabled = true` opts in to a matching Inspector finding and ECR image-digest lookup for a positive ECS/EKS `inUseCount`. The default is `false`: the caller must first prove that its Inspector API can read the finding account and Region. Positive evidence is labeled `observed in use`, which is distinct from verified current deployment; zero, missing, mismatched, or inaccessible evidence stays `unknown` and never proves the image is unused. [Amazon Inspector's ECS/EKS image-use feed](https://docs.aws.amazon.com/inspector/latest/user/scanning-ecr.html) can lag by 36 hours for new images and then refreshes daily. The worker refreshes an unchanged finding's lookup on its next full reconciliation after 24 hours and discards a previous positive observation when that refresh fails. A successful lookup with no matching use remains `unknown`; a failed lookup has no freshness timestamp and is retried by later worker reconciliation. The short EventBridge router records unknown deployment immediately; Inspector reads run in the scheduled worker with at most three pages and a five-second deadline checked between API calls. An incomplete lookup stays unknown without a freshness timestamp. A cached positive observation is accepted only while it is less than 24 hours old; reconciliation failure can delay correction of an already open alert. This does not cover Lambda container images or other registries. A central monitoring account can read member-account findings through Security Hub without having access to the same findings through Inspector `ListFindings`; leave the lookup disabled until cross-account evidence access is verified. `ExploitAvailable=YES` means exploit availability, not observed exploitation. For automatic P1, observed image use must be paired with a production label and independent verified exposure plus exploit availability, or independent verified active exploitation for a Critical finding. ECR storage, image tags, and Inspector image-use counts do not establish exposure or an incident. The current lookup does not collect network exposure or active exploitation, so image use alone remains P2 for Critical findings and digest-only for High findings.

Routine HIGH Inspector container findings go to the daily digest. Non-container CRITICAL findings retain the existing P1 default. In grouped delivery, every distinct new active HIGH or CRITICAL GuardDuty finding created after cutover gets its own stable Opsgenie incident and immediate Slack notification by default; retries of the same finding are deduplicated. Previously alerted GuardDuty findings retain their existing incident alias during upgrade to avoid duplicate pages. Configured urgent types and CRITICAL findings reach P1, while other HIGH findings default to P2. Port probing defaults to P2 even if its prefix is in the urgent list. GuardDuty type prefixes match the native classifier within Security Hub ASFF `Types`, such as `UnauthorizedAccess:` in `TTPs/Initial Access/UnauthorizedAccess:EC2-SSHBruteForce`. `guardduty_port_probe_p1=true` is an explicit override. Grouped EventBridge delivery includes resolution updates; when Security Hub leaves the provider's `UpdatedAt` unchanged, the ledger uses a newer `ProcessedAt` to order customer workflow changes. A pre-upgrade ledger row without `ProcessedAt` must first receive a refreshed snapshot before a same-timestamp workflow change can be safely ordered. HIGH non-container findings require exploit availability and explicit public exposure by default. `ExploitAvailable=YES` is not evidence of active exploitation. Per-finding mode retains its previous behavior.

**Opsgenie routing:** P2 creates a real Opsgenie alert for investigation and may notify or page responders; P1 is the paging tier. The module does not configure Opsgenie teams, routing rules, notification policies, schedules, or personal notification rules. Before rollout, the Opsgenie owner must route `securityhub-grouped` P2 alerts to the investigation path without voice/SMS/on-call paging, route P1 to the on-call escalation and active contact methods, and verify a P2-to-P1 priority update on the same alias with a canary. Where supported, configure a [team notification policy](https://support.atlassian.com/opsgenie/docs/create-and-manage-team-alert-policies/) that matches the `securityhub-grouped` tag and P2 priority and suppresses recipient notifications while leaving the alert visible. Otherwise use team routing and recipient rules that provide the intended P2 behavior. Disable repeat or auto-restart notifications for this integration unless the incident response policy explicitly requires them. [Opsgenie says a higher priority restarts the notification flow](https://support.atlassian.com/opsgenie/docs/update-alert-priority-level/), but the actual team and user configuration still determines who receives it. Verify that a second Critical CVE updates the same application alert without a fresh notification. Set `paging.ecr_critical_unknown_priority` to `P1` to preserve the older ECR behavior or `DIGEST` to omit the P2 alert; both choices should be reviewed by the owner.

The worker reconciles every 15 minutes and publishes at most one daily Slack digest after `daily_digest.hour_utc` (default 08:00 UTC). Its main message contains the severity distribution, active findings, distinct resources and vulnerabilities, quiet versus confirmed resolved groups, the top `daily_digest.max_groups` non-container remediation groups (default 5), and compact Inspector application summaries. Application summaries count distinct vulnerabilities and image digests without printing the digests. All active records remain in Security Hub. An empty day still produces a zero-findings brief. The stable ranking is: highest active severity, active GuardDuty, explicit public exposure, affected resource count, new or escalated finding count, then group label and key. Finding volume cannot outrank a Critical group. Quiet means no actionable finding after `quiet_period_minutes` (default 60); it does not imply remediation. An Opsgenie incident closes only after no active finding still qualifies for paging for the configured quiet period; routine active findings remain in the digest and Security Hub. A later qualifying finding can reopen the incident. A P1 incident with remaining P2 findings transitions to P2 after the P1 finding resolves; the P1 claim is cleared so a later P1 can notify again. Resolved snapshots remain in the ledger for `finding_retention_days` (default 365) before DynamoDB TTL can remove them; active snapshots do not expire.

The scheduled worker bootstraps with a strongly consistent parallel scan of the existing ledger, including old archived findings and open incident markers. It retries this scan until the first daily acknowledgement succeeds, or completes one scan when the daily brief is disabled. After a successful daily brief, a DynamoDB `notification-state` index lets later runs query active findings, recent inactive changes, unresolved legacy alerts, and open incident markers; archived history is not scanned every 15 minutes. New inactive findings use a date bucket. Newly accepted changes also receive a durable `notification_digest_pending` marker and a fresh `notification_pending_at`, even if their Security Hub timestamp is old. A staged daily outbox conditionally acknowledges the exact finding versions included in the brief before SNS publish. A row omitted by the eventually consistent index stays pending for a later brief. Open incident markers retain a small group snapshot so quiet-period closure remains retryable after all findings become inactive. The index is eventually consistent; the worker deduplicates overlapping states and uses the quiet period before closing an alert. Adding the index to a populated table has an AWS backfill period and should be reviewed in the state-backed plan.

Security Hub reconciliation now advances in fixed 15-minute update windows, saves its cursor with a conditional DynamoDB write, and processes at most 300 pages or 240 seconds per invocation before leaving time for the digest. It resumes from the saved page token, restarts only the current window if that token expires, and advances `reconciled_through` only after the entire target interval succeeds. During a long historical replay, a separate overlapping one-hour pass keeps routine and resolved updates current. It saves a cursor through five-minute update windows, processes at most 250 pages or 180 seconds per invocation, and resumes the remaining pages on the next run. An expired Security Hub page token restarts only its current five-minute window. A large update burst can delay this pass while it catches up; the checkpoint and progress logs retain the backlog. That quick pass records unknown deployment without Inspector reads; the checkpointed pass enriches findings and uses 50-finding pages when lookup is enabled. The first ledger bootstrap runs before historical reconciliation so it can restore grouped alerts and the daily brief promptly. Lambda concurrency is one, memory is 4096 MiB, timeout is 900 seconds, and the duration alarm fires at 720 seconds. The one-time full scan has an explicit 1,000,000-finding bound; indexed active and recent rows have the same bound. Exceeding a bound or exhausting retries raises an error and preserves retryability. A full-volume canary must measure runtime, DynamoDB reads, index backfill, and Opsgenie behavior before production rollout. The daily SNS payload includes only the displayed application summaries and their total count. The daily outbox stores a stable SNS payload and group-state work before publishing. If SNS accepts a message and the checkpoint write fails, a later invocation retries the same delivery ID and may duplicate the Slack message. The current SNS-to-Slack subscriber does not use that ID to suppress duplicate webhook posts. Once the checkpoint succeeds, group-state failures retry without republishing. SNS and webhooks are also at-least-once; the complete pipeline does not guarantee exactly-once delivery. The group-digest error alarm uses one breaching datapoint across three five-minute periods, so an intervening zero-error datapoint does not generate another ALARM notification during repeated failures.

```hcl
finding_delivery = {
  enabled               = true
  notification_mode     = "grouped"
  opsgenie_api_key      = var.opsgenie_api_key
  environment_label     = "Production"
  project_label         = "Example"
  account_label         = "Example production"
  quiet_period_minutes  = 60
  finding_retention_days = 365
  daily_digest = {
    enabled    = true
    hour_utc   = 8
    max_groups = 5
  }
  realtime = {
    enabled                = true
    guardduty_min_severity = "HIGH"
    high_requires_public_exposure = true
  }
  paging = {
    critical         = true
    high_exploitable = true
    require_public_exposure = true
    guardduty_types  = ["UnauthorizedAccess:", "Trojan:"]
    guardduty_investigation_types = ["Recon:"]
    ecr_critical_unknown_priority = "P2"
    ecr_deployment_lookup_enabled = false # Enable only after Inspector member-account access is verified.
    ecr_emergency_vulnerability_ids = []
  }
}
```

Console links open the correct finding Region and list; an exact finding deep link is not emitted where AWS console URL support cannot be verified. The Slack webhook must already be configured for the intended security channel. Terraform resource addresses and remediation keys remain stable. ECR Opsgenie aliases change to an application-level key; the reconciliation worker creates or reuses the replacement before closing historical CVE-level aliases. If an Opsgenie action fails, it retries and reaches the existing dead-letter path. Review the first plan and the Opsgenie P2 routing before applying.

Slack incoming webhooks post to the channel selected when the webhook was created. The `channel` field in `alarm_actions.slack_webhooks` names the module's subscription but cannot redirect a modern webhook. Create the webhook for the intended channel; see [Slack's incoming webhook documentation](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/).

Grouped Opsgenie incident creations, priority changes, meaningful vulnerability or risk changes, and closures publish a group-level copy to the Slack topic. Immediate P1/P2 routing uses the same `securityhub-group-<group key>` alias shown in the scheduled copy; the worker suppresses an equivalent scheduled copy. New CVEs, priority changes, and resolutions remain visible as labeled updates. Additional findings with the same vulnerability and risk facts change the counts in Opsgenie details and the daily digest without a new Slack incident message. The scheduled copy includes the incident priority, account, Region, risk evidence, affected-resource and vulnerability counts, and Security Hub link. It also includes a direct Opsgenie link when the Alert API returns an alert ID. `finding_delivery.opsgenie_web_url` can override the regional Opsgenie web base URL for tenant-specific domains.

A pending scheduled copy is kept in the existing DynamoDB group marker and retried after a failure; unchanged incidents already open before this behavior is enabled are not bulk-posted to Slack. If an older action was never confirmed in the ledger and a newer finding arrives, the latest complete group view replaces the unconfirmed copy and the old delivery ID remains on the marker for audit. Opsgenie SNS publication precedes immediate Slack publication, so a Slack publish failure does not prevent the urgent Opsgenie attempt. SNS and the webhook are at-least-once; a crash after SNS acceptance can duplicate a copy with the same stable delivery ID. Configure each project module instance's `alarm_actions.slack_webhooks` for that project's security channel, and verify the webhook's bound channel. Disable Opsgenie-to-Slack posting for AWS Security Hub alerts created by this module, or filter both the `securityhub-grouped` tag and per-finding `AWS Security Hub` source, to avoid a second Slack copy outside this module.

Per-finding API delivery shows the same `securityhub-<finding key>` Opsgenie alias on Slack creation and resolution messages. The legacy `opsgenie_endpoint` webhook path publishes to the existing high-severity SNS topic independently; Opsgenie controls the resulting alert identity. Use the API-backed mode when a shared alias and matched lifecycle are required.

### Microsoft Teams destinations

Set `finding_delivery.teams_webhooks` to one or more Teams webhook URLs and select `finding_delivery.teams_delivery`:

| Value | Teams receives |
| --- | --- |
| `none` (default) | No new Teams subscription |
| `slack` | Daily routine brief, immediate urgent messages, and grouped Opsgenie incident copies from the Slack topic |
| `opsgenie` | Urgent messages from the high-severity Opsgenie topic |
| `both` | Both topic streams |

For `both`, the same urgent finding reaches the webhook through both topics and produces two Teams messages. Teams cards summarize Security Hub findings and link to the console. The configured Teams webhook also receives delivery-failure alarms. Existing `alarm_actions.teams_webhooks` subscriptions continue to work and require no migration. Keep webhook URLs in sensitive variables.

## 🌍 Multi-Region Support and Finding Aggregation

### Region-Specific Services

**AWS Config, GuardDuty, and Macie are region-specific services.** When you deploy this Security Hub module, these submodules create resources only in the AWS provider's current region:

- **Config**: Records resource configurations in the current region only
- **GuardDuty**: Creates a detector in the current region only
- **Macie**: Enables Macie in the current region only

**To enable these services in multiple regions**, you have two options:

1. **Deploy the Security Hub module separately in each region** (using provider aliases or separate Terraform workspaces)
2. **Deploy only the submodules** (config, guardduty, macie) in additional regions while keeping Security Hub in one central region

### Inspector - Automatic Multi-Region

**AWS Inspector v2 is different** - it automatically scans resources across **ALL regions** in your account when enabled. You only need to deploy it once per account, and it handles all regions automatically.

### Security Hub Finding Aggregation

**Security Hub aggregates findings from all regions** via the finding aggregator:

- **`link_mode = "ALL_REGIONS"`** (default): Aggregates findings from all regions automatically
- **`link_mode = "SPECIFIED_REGIONS"`**: Aggregates findings only from regions listed in `specified_regions`

When you enable Config, GuardDuty, or Macie in multiple regions, their findings are automatically aggregated into your central Security Hub instance, giving you a unified view of security findings across all regions.

### Recommended Multi-Region Setup

1. **Deploy Security Hub once** in your primary/central region (e.g., `us-east-1`)
2. **Deploy Config, GuardDuty, and Macie submodules** in each region where you have resources
3. **Deploy Inspector once** (it automatically handles all regions)
4. **Configure Security Hub finding aggregator** with `link_mode = "ALL_REGIONS"` to aggregate all findings

This setup provides comprehensive security coverage across all regions while maintaining a centralized Security Hub dashboard.

### CIS v5 migration

The default standards are AWS Foundational Security Best Practices v1.0.0 and CIS AWS Foundations Benchmark v5.0.0. This default change is breaking for existing deployments because Terraform will remove the v1.2.0 subscription when it applies the new default. To preserve coverage, first explicitly configure both CIS versions:

```hcl
enabled_standards = [
  "aws-foundational-security-best-practices/v/1.0.0",
  "cis-aws-foundations-benchmark/v/1.2.0",
  "cis-aws-foundations-benchmark/v/5.0.0",
]
```

Apply this override, wait until CIS v5.0.0 is `READY` and findings are available, then remove v1.2.0 from the override and apply again. New deployments use v5.0.0 and do not auto-enable v1.2.0.

`control_finding_generator` is unmanaged by default to preserve existing AWS behavior. Set it to `"SECURITY_CONTROL"` to consolidate findings across standards. In AWS Organizations, set this from the Security Hub administrator account.
